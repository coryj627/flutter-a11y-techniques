# S11 Reading and traversal order

A screen reader moves through a screen in an order that keeps its meaning:
what is shown as one column is read as one, and not mixed with what is
beside it, and a heading comes before what it heads. Keyboard focus reaches
the controls in the same order.

Code: [`lib/techniques/s11_reading_traversal_order/examples.dart`](../../lib/techniques/s11_reading_traversal_order/examples.dart).
Spec: [`docs/specs/S11-reading-traversal-order.md`](../specs/S11-reading-traversal-order.md).
In the app: `/t/S11`, and each example at `/t/S11/<slug>`.

Platforms: Android, iOS, and the web apply. Every good example is
Flutter's own widgets through their documented parameters; none is a
custom solution ([custom-solutions.md](../custom-solutions.md#s11-reading-and-traversal-order)).

## Why it matters

Someone who sees two columns side by side reads one, then the other: the
steps of a route in order, then what to bring. A screen reader user hears
the parts one at a time, in the order the app gives them. If that order
goes back and forth between the columns, a step is followed by an item
from the other list, and neither list makes sense.

Flutter does not read a screen in the order its widgets are written. It
sorts the parts by where they are on the screen: rows first, left to right
within a row. Two columns whose lines are level are read row by row, mixed
together, even when each column is one `Column` in the code. Whether a
layout is read mixed or by column can change with the screen's width and
the text size, because it depends on which parts' boxes overlap. The fix
has to say what belongs together.

## WCAG 2.2

- [1.3.2 Meaningful Sequence](https://www.w3.org/TR/WCAG22/#meaningful-sequence): the order of the steps, and of a list under its heading, is part of their meaning, and the [Understanding document](https://www.w3.org/WAI/WCAG22/Understanding/meaningful-sequence.html) allows two independent sections in either order "as long as they are not interleaved"; its first example is a page of columns, read from the top of one column to its bottom.
- [2.4.3 Focus Order](https://www.w3.org/TR/WCAG22/#focus-order): Tab reaches the controls; the technique keeps their order the same as the order they are read in. No example here fails it: Tab is right in all four, as [Understanding 2.4.3](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) asks (the keyboard's order on its own is [I02](I02.md)'s subject).

The sources: the iOS reference repository's
[Reading Order](https://github.com/cvs-health/ios-swiftui-accessibility-techniques/blob/main/iOSswiftUIa11yTechniques/Documentation/ReadingOrder.md)
and [Accessibility Sort Priority](https://github.com/cvs-health/ios-swiftui-accessibility-techniques/blob/main/iOSswiftUIa11yTechniques/Documentation/AccessibilitySortPriority.md),
the Android View reference's
[Accessibility Reading Order](https://github.com/cvs-health/android-view-accessibility-techniques/blob/main/doc/grouping/AccessibilityReadingOrder.md),
and the Android Compose reference's
[Accessibility Traversal Order](https://github.com/cvs-health/android-compose-accessibility-techniques/blob/main/doc/content/AccessibilityTraversalOrder.md).
All three build the same layout, columns side by side, and prefer a group
per column to an explicit index, which they call fragile.

## Good examples

| Example | How | Source |
| --- | --- | --- |
| `good-columns` | `Semantics(container: true, explicitChildNodes: true)` round each `Column`: the screen reader reads the route column, then the bring column, each part a stop of its own. A `FocusTraversalGroup` round each column keeps Tab in the same order. | iOS Reading Order (`.contain`), Android Compose (`isTraversalGroup`), Android View (one layout per column), [Flutter: Semantics.container](https://api.flutter.dev/flutter/widgets/Semantics/container.html) |
| `good-sort-keys` | The same parts laid out row by row, so that each step lines up with the item beside it, where no widget holds a column: `Semantics(container: true, sortKey: OrdinalSortKey(n))` on every part, the route 1 to 5 and the list 6 to 9. | iOS Accessibility Sort Priority, Android Compose (`traversalIndex`), [Flutter: OrdinalSortKey](https://api.flutter.dev/flutter/semantics/OrdinalSortKey-class.html) |

What makes each of them work:

- **A container per column, with `explicitChildNodes: true`.** The
  container keeps the column together; `explicitChildNodes` keeps its
  parts apart. Without it, the container joins the column's texts into one
  node, read in one go (the iOS reference's `.combine`, not `.contain`).
- **A focus group per column as well.** A semantics container does nothing
  for Tab, and a focus group nothing for the screen reader
  ([FL-420](../flutter-limitations.md#fl-420)). Here the Bring column is
  shorter, so its button is higher on the screen, and without the groups
  Tab, which also goes by position, reached Save list before Save route in
  the widget tests at five of the six sizes measured (not measured on a
  device); with them, Save route comes first everywhere.
- **A key on every part, or on none.** A part with no key keeps its place
  by position and splits the keyed parts round it into runs that are
  sorted apart ([FL-340](../flutter-limitations.md#fl-340),
  `bad-key-missing`).
- **The key outside `MergeSemantics`.** A key on something that is merged
  into another node, as each button is merged by its `TestId`, does not
  order anything ([FL-341](../flutter-limitations.md#fl-341)).
- **Prefer containers.** As the references say, an index on every part has
  to be kept up to date by hand; a container per column follows the
  layout.
- **A focus outline** from each button's own `style`: Material's focus tint
  on a `TextButton` is under 3:1 ([FL-430](../flutter-limitations.md#fl-430)).

## Bad examples

Each has one defect, and the tests assert that the defect is present.

| Example | Defect | Fails |
| --- | --- | --- |
| `bad-columns-mixed` | `good-columns` without the containers: read across the columns, both headings first, then a step, an item, a step. Tab is still right, down one column and then the other ([FL-420](../flutter-limitations.md#fl-420)) | 1.3.2, on every platform |
| `bad-key-missing` | `good-sort-keys` with the "Bring" heading given no key: it is read second, before the route, and the list's items follow the route with no heading ([FL-340](../flutter-limitations.md#fl-340)) | 1.3.2, on every platform |

### Shared code

Used by the examples below.

```dart
/// The left column: its title and the route's steps, in order.
const routeTitle = 'Route';
const routeSteps = ['Park at the gate.', 'Climb the ridge.', 'Walk back.'];

/// The right column: its title and what to bring.
const bringTitle = 'Bring';
const bringItems = ['Water', 'A map'];

/// A column's title: a level 3 heading, under the screen's level 1 title and
/// its level 2 "Example". `headingLevel` makes it a heading on every
/// platform (FL-003, FL-005) and the right level on the web (FL-004).
class ColumnTitle extends StatelessWidget {
  const ColumnTitle(this.text, {super.key});

  final String text;

  @override
  Widget build(BuildContext context) => Semantics(
    headingLevel: 3,
    child: Text(text, style: Theme.of(context).textTheme.titleMedium),
  );
}

/// A 2 pixel outline in the page's text colour while a `TextButton` has
/// keyboard focus, through the button's own `style`, as in C12 and C18:
/// Material's own focus tint on a `TextButton` is under 3:1 against the page
/// (docs/flutter-limitations.md, FL-430).
ButtonStyle focusRing(ColorScheme colors) => ButtonStyle(
  side: WidgetStateProperty.resolveWith(
    (states) => states.contains(WidgetState.focused)
        ? BorderSide(color: colors.onSurface, width: 2)
        : null,
  ),
);

/// Holds how many times each list was saved, and ends every example with
/// the two counts, so that people and tests can see which button ran.
class Plan extends StatefulWidget {
  const Plan({super.key, required this.slug, required this.builder});

  final String slug;
  final Widget Function(BuildContext context, PlanState plan) builder;

  @override
  State<Plan> createState() => PlanState();
}

class PlanState extends State<Plan> {
  int routeSaves = 0;
  int listSaves = 0;

  /// The test identifier of the part [name] of this example.
  String id(String name) => 's11-${widget.slug}-$name';

  /// The "Save route" button.
  Widget saveRoute(BuildContext context) => TestId(
    id('save-route'),
    child: TextButton(
      style: focusRing(Theme.of(context).colorScheme),
      onPressed: () => setState(() => routeSaves++),
      child: const Text('Save route'),
    ),
  );

  /// The "Save list" button.
  Widget saveList(BuildContext context) => TestId(
    id('save-list'),
    child: TextButton(
      style: focusRing(Theme.of(context).colorScheme),
      onPressed: () => setState(() => listSaves++),
      child: const Text('Save list'),
    ),
  );

  Widget _count(String name, String text) => Semantics(
    key: ValueKey<String>(id(name)),
    identifier: id(name),
    liveRegion: true,
    child: Text(text),
  );

  @override
  Widget build(BuildContext context) {
    return Column(
      crossAxisAlignment: CrossAxisAlignment.stretch,
      spacing: 8,
      children: [
        widget.builder(context, this),
        _count('route-saves', 'Route saves: $routeSaves'),
        _count('list-saves', 'List saves: $listSaves'),
      ],
    );
  }
}

/// Two parts side by side, each half the width.
Widget sideBySide(Widget left, Widget right) => Row(
  crossAxisAlignment: CrossAxisAlignment.start,
  spacing: 16,
  children: [
    Expanded(child: left),
    Expanded(child: right),
  ],
);

/// One column of parts, top to bottom.
Widget stack(List<Widget> children) => Column(
  crossAxisAlignment: CrossAxisAlignment.start,
  spacing: 8,
  children: children,
);

/// The route column's parts: its title, its steps, and its button.
List<Widget> routeColumn(BuildContext context, PlanState plan) => [
  const ColumnTitle(routeTitle),
  for (final step in routeSteps) Text(step),
  plan.saveRoute(context),
];

/// The bring column's parts: its title, its items, and its button.
List<Widget> bringColumn(BuildContext context, PlanState plan) => [
  const ColumnTitle(bringTitle),
  for (final item in bringItems) Text(item),
  plan.saveList(context),
];

/// Gives [child] its place, [order], in the screen reader's order.
Widget readAt(double order, Widget child) =>
    Semantics(container: true, sortKey: OrdinalSortKey(order), child: child);

/// The two columns built row by row. [bringTitleOrder] is the bring
/// column's title's place in the reading order, or null for none.
Widget rowBuilt(
  BuildContext context,
  PlanState plan, {
  double? bringTitleOrder = 6,
}) {
  Widget title = const ColumnTitle(bringTitle);
  if (bringTitleOrder != null) title = readAt(bringTitleOrder, title);
  return stack([
    sideBySide(readAt(1, const ColumnTitle(routeTitle)), title),
    sideBySide(readAt(2, Text(routeSteps[0])), readAt(7, Text(bringItems[0]))),
    sideBySide(readAt(3, Text(routeSteps[1])), readAt(8, Text(bringItems[1]))),
    sideBySide(readAt(4, Text(routeSteps[2])), const SizedBox.shrink()),
    sideBySide(
      readAt(5, plan.saveRoute(context)),
      readAt(9, plan.saveList(context)),
    ),
  ]);
}
```

### `good-columns`

```dart
/// Each column is a semantics container, so a screen reader reads one
/// column and then the other, and keeps each part a stop of its own with
/// `explicitChildNodes` (without it the container joins the column's texts
/// into one node). Each column is also a `FocusTraversalGroup`, so Tab
/// reaches the buttons in the same order whatever their heights: the right
/// column's button is higher on the screen, and without the groups Tab,
/// which goes by position, reached it first in the widget tests at most
/// sizes measured.
class GoodColumns extends StatelessWidget {
  const GoodColumns({super.key});

  @override
  Widget build(BuildContext context) {
    return Plan(
      slug: 'good-columns',
      builder: (context, plan) => sideBySide(
        FocusTraversalGroup(
          child: Semantics(
            container: true,
            explicitChildNodes: true,
            child: stack(routeColumn(context, plan)),
          ),
        ),
        FocusTraversalGroup(
          child: Semantics(
            container: true,
            explicitChildNodes: true,
            child: stack(bringColumn(context, plan)),
          ),
        ),
      ),
    );
  }
}
```

### `good-sort-keys`

```dart
/// The same two columns laid out row by row, so that each step lines up
/// with the item beside it: no widget holds a column, so no container can
/// keep one together. Every part is given its place in the reading order
/// with an `OrdinalSortKey`, the route's parts 1 to 5 and the list's 6 to
/// 9. Every part needs one: a part with no key keeps its place by position
/// (`bad-key-missing`). The key goes outside the button's `TestId`, whose
/// `MergeSemantics` would drop it (FL-341). The two buttons share the last
/// row, so Tab, which goes by position, reaches them in the reading order.
class GoodSortKeys extends StatelessWidget {
  const GoodSortKeys({super.key});

  @override
  Widget build(BuildContext context) {
    return Plan(
      slug: 'good-sort-keys',
      builder: (context, plan) => rowBuilt(context, plan),
    );
  }
}
```

### `bad-columns-mixed`

```dart
class BadColumnsMixed extends StatelessWidget {
  const BadColumnsMixed({super.key});

  @override
  Widget build(BuildContext context) {
    return Plan(
      slug: 'bad-columns-mixed',
      // Defect: no semantics container round either column. Flutter orders
      // what a screen reader reads by position, row by row, so it goes back
      // and forth between the two columns: Route, Bring, Park at the gate.,
      // Water, and so on. Tab still goes down one column, then the other.
      builder: (context, plan) => sideBySide(
        FocusTraversalGroup(child: stack(routeColumn(context, plan))),
        FocusTraversalGroup(child: stack(bringColumn(context, plan))),
      ),
    );
  }
}
```

### `bad-key-missing`

```dart
class BadKeyMissing extends StatelessWidget {
  const BadKeyMissing({super.key});

  @override
  Widget build(BuildContext context) {
    return Plan(
      slug: 'bad-key-missing',
      // Defect: the "Bring" title has no sort key. A part with no key keeps
      // its place by position and splits the keyed parts round it into
      // runs that are sorted apart (FL-340), so it is read second, before
      // the route's steps, and nothing heads the list that follows them.
      builder: (context, plan) =>
          rowBuilt(context, plan, bringTitleOrder: null),
    );
  }
}
```

## What each platform exposes

Measured on Flutter 3.47.5. Screen reader speech is from the transcripts
below; the rest from the tree tests and the probe
([evidence/probes/s11](../evidence/probes/s11/README.md)).

| | Web | Android | iOS |
| --- | --- | --- | --- |
| What carries the order | the order of the elements in the document, which Flutter writes in its reading order; no `aria-owns` or `aria-flowto` | the order of the nodes in the tree, each linked to its sibling before it (`traversalAfter`) | the order of the accessibility elements |
| The order the screen reader moved in | the document's order (VoiceOver in Chromium and WebKit, the four examples) | TalkBack's own "next": the tree's order | VoiceOver's own swipes: the same order |
| Two columns, a container each (`good-columns`) | each column's parts in turn, at 1280 and 320 pixels wide | the same | the same |
| Row by row, a key on every part (`good-sort-keys`) | the column order | the same | the same |
| No container (`bad-columns-mixed`) | row by row, both headings first | row by row on the local emulator and at CI's size | row by row on the iPhone 17 simulator |
| One part with no key (`bad-key-missing`) | Route, Bring, the steps, Save route, the items, Save list | the same | the same |
| Tab | Back, Save route, Save list, then out of the page, in every example | the same, and round to Back | two Tabs reach Save route, three Save list |

Things to know:

- **Every platform reads in the framework's order**, so a reading order
  tested in a widget test is the order on every platform, for the same
  layout (in the probe, on the web, a traversal child grafted onto a node
  elsewhere kept its place in the document and was moved only by
  `aria-owns` in the accessibility tree; no example has one). The layout is the catch: the order rests on where the parts
  are, and the test font is wider than a real one, so `bad-columns-mixed`
  is read in other mixed orders in the widget tests than on a device
  ([FL-420](../flutter-limitations.md#fl-420)).
- **XCUITest's list of elements is not VoiceOver's order** once an
  element has children; the VoiceOver walk is what checks the order on
  iOS.
- **A sort key does not move Tab.** Where a key reorders what the
  keyboard can reach, give the keyboard the same order with
  `OrderedTraversalPolicy` and `FocusTraversalOrder` ([I02](I02.md)). On
  the web, two orders that end on different controls make Tab go round
  and never leave the page ([FL-421](../flutter-limitations.md#fl-421)).
- **Right-to-left is not covered.** In the probe, a `Directionality`
  round the columns swapped them on the screen but not the reading order;
  see the spec.

## Flutter limitations

Found on Flutter 3.47.5. Full detail is in the
[limitations log](../flutter-limitations.md).

- [FL-340](../flutter-limitations.md#fl-340): a node with no sort key keeps its place by position and splits the keyed nodes round it into runs that are sorted apart.
- [FL-341](../flutter-limitations.md#fl-341): a sort key inside `MergeSemantics` does not order the merged node.
- [FL-420](../flutter-limitations.md#fl-420): the screen reader's order is by position, and set apart from the keyboard's; extended with what S11 measured.
- [FL-421](../flutter-limitations.md#fl-421): on the web, a sort key that ends the reading order on a different control from Tab makes Tab go round; extended.
- [FL-430](../flutter-limitations.md#fl-430): Material's focus tint on a `TextButton` is under 3:1.
- [FL-002](../flutter-limitations.md#fl-002): Enter does not activate a `CupertinoButton` on the web, which is why there is no Cupertino example.
