# F03 Keyboard types

A text field asks for the on-screen keyboard that fits what it takes, says
what its Enter key does, and, when it collects information about the
user, names that information with an autofill hint, so that the platform
can offer the right keys and fill the field in.

Code: [`lib/techniques/f03_keyboard_types/examples.dart`](../../lib/techniques/f03_keyboard_types/examples.dart).
Spec: [`docs/specs/F03-keyboard-types.md`](../specs/F03-keyboard-types.md).
In the app: `/t/F03`, and each example at `/t/F03/<slug>`.

A field's label is [F01 Text fields and labels](F01.md), and its
instructions F02 Input instructions (not on main yet, so not linked).
Autofill in depth, beyond the hints set here, is F04 Autofill and input
purpose (not built yet).

## Why it matters

The on-screen keyboard is how most people on a phone type. A field for a
phone number that opens the dial pad, or an email field with "@" on the
first page, saves keystrokes; a name field that opens the number pad
cannot be filled in with the keyboard at all. That matters most to people
who type slowly or with effort: with a tremor, with a switch, with a head
pointer, or one key at a time with a screen reader.

Naming the purpose of a field (its name, email, phone number, username,
password) lets the platform fill it in from what it already knows, so
those people type less, and people with memory or cognitive disabilities
do not have to recall or retype their details. It also lets software that
adapts a page, with icons or familiar words, know what each field is for.
That is WCAG 1.3.5.

## WCAG 2.2

- [1.3.5 Identify Input Purpose](https://www.w3.org/TR/WCAG22/#identify-input-purpose) (AA): a field that collects information about the user, for one of WCAG's [input purposes](https://www.w3.org/TR/WCAG22/#input-purposes), has that purpose in a form software can read. In Flutter that is `autofillHints`.

The keyboard type is not what 1.3.5 measures. The
[Understanding document](https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html)
does not mention keyboards, and no WCAG 2.2 criterion requires a
particular on-screen keyboard, so the keyboard examples below are good or
bad practice with no criterion failed. 1.3.5 covers information about the
user only: an amount needs no hint.

On the web the sufficient technique is
[H98](https://www.w3.org/WAI/WCAG22/Techniques/html/H98): an
[`autocomplete`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/autocomplete)
token that matches the field's purpose. The keyboard is chosen by `type`
and [`inputmode`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/inputmode).
On Android and iOS, [WCAG2ICT](https://www.w3.org/TR/wcag2ict-22/#identify-input-purpose)
applies 1.3.5 as written where the platform has attributes for the
meaning of a field: Android's autofill hints and iOS's text content
types, which Flutter's `autofillHints` sets.

## Bad examples

Each has one defect, and the tests assert that the defect is present.

| Example | Defect | Fails |
| --- | --- | --- |
| `bad-number-for-name` | A name field with `TextInputType.number`. The on-screen keyboard has digits only, so a name cannot be typed with it on Android or iOS. On the web it gets the general keyboard ([FL-162](../flutter-limitations.md#fl-162)). | None as written. The purpose is given |
| `bad-default-keyboard` | An email field left with the default keyboard: "@" is not on its first page. | None as written |
| `bad-no-purpose` | A name field with the name keyboard and no autofill hint: nothing names its purpose, so the platform cannot offer to fill it in. | 1.3.5 on Android and iOS; on the web `good-contact`'s name field fails it as well ([FL-161](../flutter-limitations.md#fl-161)) |
| `bad-email-no-suggestions` | An email field with `enableSuggestions: false`. On Android the engine turns its keyboard into the general one, with no "@" ([FL-160](../flutter-limitations.md#fl-160)); on iOS and the web it keeps the email keyboard. | None as written |

None of these defects is heard: a screen reader reads each bad example as
it reads the good one.

class _Demo extends StatefulWidget {

  final String slug;
  final List<Widget> Function(BuildContext context, VoidCallback changed)

  @override
  State<_Demo> createState() => _DemoState();

          identifier: 'f03-${widget.slug}-count',
          liveRegion: true,
          child: Text('Changes: $_count'),

    );

### `good-cupertino`

```dart
/// A Cupertino field takes the same keyboard type and autofill hints. It
/// has no label of its own (FL-016), so it is given the row's text as its
/// name, and that text is left out of the semantics so it is not read
/// twice.
class GoodCupertino extends StatelessWidget {
  const GoodCupertino({super.key});

  @override
  Widget build(BuildContext context) {
    Widget row({
      required String label,
      required String id,
      required TextInputType keyboardType,
      required String hint,
      required TextInputAction action,
      required VoidCallback changed,
    }) {
      return CupertinoFormRow(
        // Less padding than the default, so that the label and the field
        // fit side by side at 200% text on a narrow phone.
        padding: const EdgeInsets.symmetric(horizontal: 8, vertical: 6),
        prefix: ExcludeSemantics(child: Text(label)),
        child: TestId(
          id,
          child: Semantics(
            label: label,
            child: CupertinoTextField.borderless(
              keyboardType: keyboardType,
              autocorrect: false,
              autofillHints: [hint],
              textInputAction: action,
              onChanged: (_) => changed(),
            ),
          ),
        ),
      );
    }

    return _Demo(
      slug: 'good-cupertino',
      builder: (context, changed) => [
        CupertinoFormSection.insetGrouped(
          margin: EdgeInsets.zero,
          children: [
            row(
              label: 'Email',
              id: 'f03-good-cupertino-email',
              keyboardType: TextInputType.emailAddress,
              hint: AutofillHints.email,
              action: TextInputAction.next,
              changed: changed,
            ),
            row(
              label: 'Phone',
              id: 'f03-good-cupertino-phone',
              keyboardType: TextInputType.phone,
              hint: AutofillHints.telephoneNumber,
              action: TextInputAction.done,
              changed: changed,
            ),
          ],
        ),
      ],
    );
  }
}
```

## What each platform exposes

Measured on Flutter 3.47.5.

| | Web | Android | iOS |
| --- | --- | --- | --- |
| How the keyboard was read | the `<input>`'s `type`, `inputmode`, and `enterkeyhint` | the editor's input type and IME action in `dumpsys input_method`, and the keys in Gboard's window | the keys and return key in `app.keyboards` |
| Name (`TextInputType.name`) | `type="text"`, no `inputmode` | input type `0xa061` (person name, capital words); letters | letters and a "phone pad" key |
| Email (`emailAddress`) | `inputmode="email"` | `0x21`; "@" on the first page | "@" and "." |
| Phone (`phone`) | `type="tel"` | `0x3`; the dial pad | the phone pad, no return key ([FL-163](../flutter-limitations.md#fl-163)) |
| Decimal (`numberWithOptions(decimal: true)`) | nothing, even on a phone ([FL-162](../flutter-limitations.md#fl-162)) | `0x2002`; digits and "." | the decimal pad, no return key |
| Number (`bad-number-for-name`) | nothing ([FL-162](../flutter-limitations.md#fl-162)) | `0x2`; digits only | the number pad: digits only, no return key |
| `textInputAction` | `enterkeyhint` on a phone only | IME action Next or Done; the key's label | return key "next" or "done" |
| Autofill hint | lost: `autocomplete="off"`, except "email" on an email field ([FL-161](../flutter-limitations.md#fl-161)) | given to the autofill framework as `personName`, `emailAddress`, `phoneNumber`, `username`, `password` | the text content type (read in the source); "Passwords" above the keyboard for the username and the password |
| Password (`obscureText`) | `type="password"`; `autocomplete="current-password"` once focused | the password flag; "Password", "password. Edit box" | a text field until edited, a secure text field while edited ([FL-042](../flutter-limitations.md#fl-042)) |
| Screen reader on a field | "Name edit text"; a phone field "Phone telephone" (Chromium) or "Phone telephone number field" (WebKit) | "Name", "Edit box" | "Name Text field Double tap to edit." |
| Screen reader on the password | "Password secure text field" | "Password", "password. Edit box"; filled, "password. 3 characters" | "Password Text field"; while edited, "Password Secure text field Is editing •••" |

Things to know:

- **Set all three.** `keyboardType` for the keys, `textInputAction` for
  the Enter key, and `autofillHints` for a field about the user. Add
  `textCapitalization` for a name and `autocorrect: false` for an address
  or a username, as the Compose reference does.
- **Keep suggestions on for an email field** on Android (FL-160).
- **Group sign-in fields** in an `AutofillGroup`, so the platform fills
  them together.
- **Use `obscureText` for a password.** A password keyboard type does not
  hide the text. TalkBack then says "password", reads a length and not
  the text, and VoiceOver on iOS says "Secure text field" while the field
  is edited.
- **On iOS a pad cannot be put away** (FL-163). Give a number or phone
  field a way to end editing if the screen needs the space.
- **On the web only the email keyboard type and the password survive**
  as a purpose (FL-161), and only email, phone, and URL as a keyboard
  (FL-162).
- **Almost none of this is heard.** A screen reader reads a field the
  same whatever its keyboard or its purpose, so a mistake here is found
  only by looking at the keyboard or the tree. The exception is a phone
  field on the web, whose `type="tel"` VoiceOver names ("Phone
  telephone").

## Flutter limitations

Found on Flutter 3.47.5. Full detail is in the
[limitations log](../flutter-limitations.md).

- [FL-160](../flutter-limitations.md#fl-160): on Android `enableSuggestions: false` on an email field gives the general keyboard, with no "@" (`bad-email-no-suggestions`). Workaround: leave suggestions on and turn off only `autocorrect`.
- [FL-161](../flutter-limitations.md#fl-161): on the web autofill hints do not reach `autocomplete`; it is "off" for every field but an email field ("email", from its keyboard type) and an obscured field once focused. No workaround: the web is a limitation for this technique.
- [FL-162](../flutter-limitations.md#fl-162): on the web the number and decimal keyboard types leave nothing in the page, so a phone's browser shows its general keyboard. No workaround.
- [FL-163](../flutter-limitations.md#fl-163): on iOS the number, decimal, and phone pads have no return key, and a tap outside the field does not end editing, so the keyboard stays up. A workaround (`onTapOutside`) is described and not built.
- [FL-042](../flutter-limitations.md#fl-042): on iOS an obscured field is a secure text field only while it is being edited. Confirmed here.
- [FL-015](../flutter-limitations.md#fl-015) and [FL-016](../flutter-limitations.md#fl-016) apply to these fields as to any: TalkBack drops the label of a filled field, and a Cupertino field needs `Semantics(label:)`.
