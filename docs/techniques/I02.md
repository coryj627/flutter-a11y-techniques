# I02 Keyboard focus order

Tab and Shift+Tab move through the controls in an order that keeps their
meaning: down one column before the next, each list before the action
that ends it.

Code: [`lib/techniques/i02_focus_order/examples.dart`](../../lib/techniques/i02_focus_order/examples.dart).
Spec: [`docs/specs/I02-focus-order.md`](../specs/I02-focus-order.md).
In the app: `/t/I02`, and each example at `/t/I02/<slug>`.

Making a control reachable at all is [I01 Focusable and clickable
controls](I01.md). Moving focus from code, other keys, Escape and keyboard
traps, and how focus looks each have an entry of their own (I03, I04, I08,
and V14), not built yet. The order a screen reader moves in is S11 Reading
and traversal order; the last section here says where the two meet.

## Why it matters

Someone who uses a keyboard, a switch, or any device that moves from
control to control meets a screen one control at a time, in the order
the app gives. If that order goes back and forth between two lists, they
fill in one list in among the other's choices; if a choice comes after
the button that saves the form, they save before they have met it.

Flutter decides the order by where controls are on the screen, row by
row, and not by how the layout is built, as Android Views, Compose, and
HTML do. Two lists side by side, with their rows level, are reached row
by row unless each list is grouped. And the keyboard's order and a screen
reader's order are set by different widgets: fixing one leaves the other
as it was.

## WCAG 2.2

- [2.4.3 Focus Order](https://www.w3.org/TR/WCAG22/#focus-order): the controls of the plan are reached in an order that keeps which list each choice belongs to, and every choice comes before the button that saves them. Both bad examples fail it in the way the Understanding document's own failing example does, a form whose tab order moves between its sections.
- [2.1.1 Keyboard](https://www.w3.org/TR/WCAG22/#keyboard): every control is reached and operated from the keyboard, forwards and backwards.

## Good examples

| Example | How | Source |
| --- | --- | --- |
| `good-material` | Each column of `CheckboxListTile`s inside a `FocusTraversalGroup`: Tab goes down one column, then the other, then to Save plan. | [Flutter: FocusTraversalGroup](https://api.flutter.dev/flutter/widgets/FocusTraversalGroup-class.html); [Android Compose: Keyboard Focus Order](https://github.com/cvs-health/android-compose-accessibility-techniques/blob/main/doc/interactions/KeyboardFocusOrder.md) (a `Row` of two `Column`s) |
| `good-cupertino` | The same with `CupertinoCheckbox`es, each merged with its text as in F07, and a `CupertinoButton.filled`. | [Flutter: Understanding Flutter's keyboard focus system](https://docs.flutter.dev/ui/interactivity/focus) |
| `good-ordered` | The same choices laid out row by row, so no widget holds a column. `FocusTraversalGroup(policy: OrderedTraversalPolicy())` and a `FocusTraversalOrder` with a `NumericFocusOrder` on every control give the order; an `OrdinalSortKey` with the same number on each gives the screen reader the same order. | [Flutter: OrderedTraversalPolicy](https://api.flutter.dev/flutter/widgets/OrderedTraversalPolicy-class.html); [Android View: Keyboard and Accessibility Focus Order](https://github.com/cvs-health/android-view-accessibility-techniques/blob/main/doc/grouping/KeyboardAndAccessibilityFocusOrder.md) (`nextFocusForward` where the layout cannot give the order) |

In every example each column is also a semantics container, so that
screen readers read one list and then the other. That is S11's subject;
it is here because without it screen readers mix the lists on some
screens, and it does nothing for the keyboard.

## Bad examples

Each has one defect, and the tests assert that the defect is present.

| Example | Defect | Fails |
| --- | --- | --- |
| `bad-columns-mixed` | `good-material` without the `FocusTraversalGroup`s. Tab goes Map, Weather, Water, Closures, First aid: back and forth between the two lists. A screen reader still reads them one at a time ([FL-420](../flutter-limitations.md#fl-420)). | 2.4.3 |
| `bad-order-missing` | `good-ordered` with no `FocusTraversalOrder` on First aid. `OrderedTraversalPolicy` puts a control with no order after all the others, so Tab reaches First aid after Save plan. On the web Tab then goes round the last four controls and never leaves the page ([FL-421](../flutter-limitations.md#fl-421)). | 2.4.3 |

### Shared code

Used by the examples below.

```dart
/// The choices of every example: what to pack, on the left, and what to be
/// sent, on the right. The order they are meant to be reached in is down
/// the left column, then down the right one, then the Save button.
const _pack = [('map', 'Map'), ('water', 'Water'), ('aid', 'First aid')];
const _sendMe = [('weather', 'Weather'), ('closures', 'Closures')];

/// Holds which boxes are checked and how many times the plan was saved, and
/// ends every example with the count, so that people and tests can see
/// what a key did.
class _Plan extends StatefulWidget {
  const _Plan({required this.slug, required this.builder});

  final String slug;
  final List<Widget> Function(BuildContext context, _PlanState plan) builder;

  @override
  State<_Plan> createState() => _PlanState();
}

class _PlanState extends State<_Plan> {
  final Set<String> _checked = {};
  int _saves = 0;

  bool isChecked(String key) => _checked.contains(key);

  void toggle(String key) => setState(
    () => _checked.contains(key) ? _checked.remove(key) : _checked.add(key),
  );

  void save() => setState(() => _saves++);

  /// The test identifier of the control [key] of this example.
  String id(String key) => 'i02-${widget.slug}-$key';

  @override
  Widget build(BuildContext context) {
    return Column(
      crossAxisAlignment: CrossAxisAlignment.stretch,
      spacing: 16,
      children: [
        ...widget.builder(context, this),
        Semantics(
          key: ValueKey<String>(id('count')),
          identifier: id('count'),
          liveRegion: true,
          child: Text('Saves: $_saves'),
        ),
      ],
    );
  }
}

/// The title over a column of choices.
class _Title extends StatelessWidget {
  const _Title(this.text);

  final String text;

  @override
  Widget build(BuildContext context) => Padding(
    padding: const EdgeInsets.only(bottom: 4),
    child: Text(text, style: Theme.of(context).textTheme.titleMedium),
  );
}

/// A column of choices under its title. The semantics container keeps the
/// column together for screen readers, which otherwise read side-by-side
/// columns row by row, as Tab does; reading order is S11's subject. It
/// does nothing for the keyboard.
class _Choices extends StatelessWidget {
  const _Choices(this.title, this.children);

  final String title;
  final List<Widget> children;

  @override
  Widget build(BuildContext context) => Semantics(
    container: true,
    child: Column(
      crossAxisAlignment: CrossAxisAlignment.stretch,
      children: [_Title(title), ...children],
    ),
  );
}

/// Two columns side by side, their rows level with each other.
class _TwoColumns extends StatelessWidget {
  const _TwoColumns({required this.left, required this.right});

  final Widget left;
  final Widget right;

  @override
  Widget build(BuildContext context) => Row(
    crossAxisAlignment: CrossAxisAlignment.start,
    spacing: 16,
    children: [
      Expanded(child: left),
      Expanded(child: right),
    ],
  );
}

/// A Material checkbox and its text as one control.
Widget _materialBox(_PlanState plan, (String, String) choice) => TestId(
  plan.id(choice.$1),
  child: CheckboxListTile(
    contentPadding: EdgeInsets.zero,
    controlAffinity: ListTileControlAffinity.leading,
    value: plan.isChecked(choice.$1),
    onChanged: (_) => plan.toggle(choice.$1),
    title: Text(choice.$2),
  ),
);

Widget _materialSave(_PlanState plan) => Align(
  alignment: AlignmentDirectional.centerStart,
  child: TestId(
    plan.id('save'),
    child: FilledButton(onPressed: plan.save, child: const Text('Save plan')),
  ),
);

/// Gives [child] its place, [order], in the keyboard's order and in the
/// screen reader's, so that the two agree.
Widget _numbered(double order, Widget child) => FocusTraversalOrder(
  order: NumericFocusOrder(order),
  child: _readAt(order, child),
);

/// Gives [child] its place, [order], in the screen reader's order only.
Widget _readAt(double order, Widget child) =>
    Semantics(container: true, sortKey: OrdinalSortKey(order), child: child);
```

### `good-material`

```dart
/// Each column is a `FocusTraversalGroup`, so Tab goes down the first
/// column before it moves to the second.
class GoodMaterial extends StatelessWidget {
  const GoodMaterial({super.key});

  @override
  Widget build(BuildContext context) {
    return _Plan(
      slug: 'good-material',
      builder: (context, plan) => [
        _TwoColumns(
          left: FocusTraversalGroup(
            child: _Choices('Pack', [
              for (final c in _pack) _materialBox(plan, c),
            ]),
          ),
          right: FocusTraversalGroup(
            child: _Choices('Send me', [
              for (final c in _sendMe) _materialBox(plan, c),
            ]),
          ),
        ),
        _materialSave(plan),
      ],
    );
  }
}
```

/// The same with Cupertino controls. `CupertinoCheckbox` takes keyboard
/// focus; it has no text of its own, so each one is merged with its text,
/// as in F07.
class GoodCupertino extends StatelessWidget {
  const GoodCupertino({super.key});

  Widget _box(_PlanState plan, (String, String) choice) => TestId(
    plan.id(choice.$1),
    child: GestureDetector(
      behavior: HitTestBehavior.opaque,
      onTap: () => plan.toggle(choice.$1),
      child: ConstrainedBox(
        constraints: const BoxConstraints(minHeight: 48),
        child: Row(
          spacing: 8,
          children: [
            CupertinoCheckbox(
              value: plan.isChecked(choice.$1),
              onChanged: (_) => plan.toggle(choice.$1),
            ),
            Flexible(child: Text(choice.$2)),
          ],
        ),
      ),
    ),
  );

  @override
  Widget build(BuildContext context) {
    return _Plan(
      slug: 'good-cupertino',
      builder: (context, plan) => [
        _TwoColumns(
          left: FocusTraversalGroup(
            child: _Choices('Pack', [for (final c in _pack) _box(plan, c)]),
          ),
          right: FocusTraversalGroup(
            child: _Choices('Send me', [
              for (final c in _sendMe) _box(plan, c),
            ]),
          ),
        ),
        Align(
          alignment: AlignmentDirectional.centerStart,
          child: TestId(
            plan.id('save'),
            child: CupertinoButton.filled(
              onPressed: plan.save,
              child: const Text('Save plan'),
            ),
          ),
        ),
      ],
    );
  }
}

### `good-ordered`

```dart
/// When no widget holds a column, as here where the choices are laid out
/// row by row, the order is given by number: `OrderedTraversalPolicy` and
/// `FocusTraversalOrder` for the keyboard, and sort keys for screen readers.
/// Every control has a number, and the numbers follow the columns.
class GoodOrdered extends StatelessWidget {
  const GoodOrdered({super.key});

  @override
  Widget build(BuildContext context) {
    return _Plan(
      slug: 'good-ordered',
      builder: (context, plan) => [
        Semantics(
          container: true,
          child: FocusTraversalGroup(
            policy: OrderedTraversalPolicy(),
            child: Column(
              crossAxisAlignment: CrossAxisAlignment.stretch,
              children: [
                _TwoColumns(
                  left: _readAt(1, const _Title('Pack')),
                  right: _readAt(5, const _Title('Send me')),
                ),
                _TwoColumns(
                  left: _numbered(2, _materialBox(plan, _pack[0])),
                  right: _numbered(6, _materialBox(plan, _sendMe[0])),
                ),
                _TwoColumns(
                  left: _numbered(3, _materialBox(plan, _pack[1])),
                  right: _numbered(7, _materialBox(plan, _sendMe[1])),
                ),
                _TwoColumns(
                  left: _numbered(4, _materialBox(plan, _pack[2])),
                  right: const SizedBox.shrink(),
                ),
                const SizedBox(height: 16),
                _numbered(8, _materialSave(plan)),
              ],
            ),
          ),
        ),
      ],
    );
  }
}
```

## What each platform exposes

Measured on Flutter 3.47.5.

| | Web | Android | iOS |
| --- | --- | --- | --- |
| Tab | Flutter's own order; Playwright reads it from `document.activeElement` | the same; `input keyevent`, read from `isFocused` | the same; `typeKey`, each stop named by what Space changes |
| Shift+Tab | the same order backwards | the same, sent as a Shift key event of its own around the Tab | the same, `typeKey` with `.shift` |
| Past the last control | focus leaves the page, except in `bad-order-missing`, where Tab goes round the last four controls ([FL-421](../flutter-limitations.md#fl-421)) | round to Back | round to Back |
| Arrow keys | scroll the page; focus stays | move to the control on that side (D-pad keys) | move to the control on that side |
| Order of the screen reader | the order of the elements in the document: one column, then the other | the order of the nodes in the tree: the same | VoiceOver's swipes: the same |
| A checkbox, to the screen reader | "Map unchecked checkbox" | "Map", "Check box", "Double-tap to toggle" ([FL-045](../flutter-limitations.md#fl-045): no state) | "Map Switch button off Double tap to toggle setting." ([FL-035](../flutter-limitations.md#fl-035)) |

The keyboard's order is not heard. A screen reader moves in its own
order, which is right in all five examples, so the two bad examples read
exactly like the good ones; only the keyboard finds their defects.

Things to know:

- **Group what belongs together.** A `FocusTraversalGroup` around each
  column, list, or card keeps Tab inside it until it is done. Flutter's
  default goes by position, row by row, wherever things line up
  ([FL-420](../flutter-limitations.md#fl-420)).
- **Set the screen reader's order as well.** The focus group does nothing
  for screen readers, and a semantics container or sort key does nothing
  for Tab. Without a container per column, screen readers on the web,
  Android, and iOS read the same two columns row by row. See S11.
- **Number every control, or none.** With `OrderedTraversalPolicy`, a
  control with no `FocusTraversalOrder` comes after all the numbered
  ones, which is the opposite of a positive `tabindex` in HTML. Prefer a
  group to numbers where the layout allows it ([Android Compose: Keyboard
  Focus Order](https://github.com/cvs-health/android-compose-accessibility-techniques/blob/main/doc/interactions/KeyboardFocusOrder.md);
  [MDN: tabindex](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/tabindex)).
- **On the web, end both orders on the same control.** Past Flutter's
  last control the browser carries on in the document's order, which is
  the screen reader's order; if that is not the end of the document, Tab
  goes round and never leaves the page ([FL-421](../flutter-limitations.md#fl-421)).
- **Put a `FocusTraversalGroup` around a scrolling view** under an app
  bar. Without one, on a scrolled screen Shift+Tab stops on Back every
  press or two and Tab past the end skips Back ([FL-422](../flutter-limitations.md#fl-422)).
- **The arrow keys move by position** on Android and iOS, which gives the
  right control in each example here; on the web they scroll. Where
  nothing is in line with the control, an arrow can leave its group
  ([probe](../evidence/probes/i02/README.md);
  [Android View: Arrow Key Focus Order](https://github.com/cvs-health/android-view-accessibility-techniques/blob/main/doc/grouping/ArrowKeyFocusOrder.md)).

## Flutter limitations

Found on Flutter 3.47.5. Full detail is in the
[limitations log](../flutter-limitations.md).

- [FL-420](../flutter-limitations.md#fl-420): Tab crosses side-by-side columns row by row by default, and the keyboard's order and the screen reader's are set by separate widgets. The good examples set both.
- [FL-421](../flutter-limitations.md#fl-421): on the web, Tab past Flutter's last control carries on in the document's order, and goes round for ever when the two orders end differently. Keep the last control last in both.
- [FL-422](../flutter-limitations.md#fl-422): on a scrolled screen the default order puts the app bar's Back button among the content. A `FocusTraversalGroup` around the scrolling view fixes it; the I02 examples do not scroll on the screens tested.
- [FL-035](../flutter-limitations.md#fl-035): a checkbox is a switch for VoiceOver on iOS.
- [FL-045](../flutter-limitations.md#fl-045): TalkBack says no state for a checkbox that is not checked.

## Where this meets the screen reader's order

The keyboard's order is this entry's; the screen reader's is S11's. They
are set by different widgets in Flutter (FL-420), so every example here
sets both and tests both, and leaves the rules for the screen reader's
order (sort keys, semantics containers) to S11. On the web the two meet
again at the ends of the order (FL-421). The spec's section 8 lists what
is handed on to I03, I04, I08, V14, I14, and S11.
