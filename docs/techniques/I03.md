# I03 Focus management

When a dialog opens, focus goes into it; when it closes, focus goes back
to the control that opened it, or to the next one when that control is
gone; and nothing opens just because a control took focus.

Code: [`lib/techniques/i03_focus_management/examples.dart`](../../lib/techniques/i03_focus_management/examples.dart).
Spec: [`docs/specs/I03-focus-management.md`](../specs/I03-focus-management.md).
In the app: `/t/I03`, and each example at `/t/I03/<slug>`.

The order Tab moves in is [I02 Keyboard focus order](I02.md). Other
keys, Escape and keyboard traps, how focus looks, and announcements each
have an entry of their own (I04, I08, V14, and [I12](I12.md)). What a
dialog is, its role, its name, and that what is behind it is inert, is
C08, C09, and C10, not built yet.

## Custom solutions

**Custom solution: not vetted by a real-world example.** `good-material`,
`good-cupertino` and `good-widgets` are custom solutions. Each is tested
here in isolation, with screen-reader transcripts, but has not been built
into a real app and tested in a user journey. Do not treat them as vetted
techniques.

What is built by hand:

- `good-material`: A focus move built by hand: after a removal, focus goes
  to the next button, with a FocusSemanticEvent timed after the route has
  gone so that the screen reader follows (FL-442).
- `good-cupertino`: The hand-built focus move of good-material, and an
  Actions so that Enter works on the web round each action sheet button
  (FL-002).
- `good-widgets`: A question drawn by hand in showGeneralDialog, with the
  hand-built focus move of good-material (FL-442).

The register of custom solutions, with the examples judged not to be one, is
[custom-solutions.md](../custom-solutions.md#i03-focus-management).

## Why it matters

Someone who moves by keyboard, switch, or screen reader meets a screen
one control at a time, from where they are. When a dialog opens, their
next step has to be in it; if focus stays behind, the next key acts on
something they cannot see. When the dialog closes, they have to carry on
from where they were; if focus drops to the top of the screen, they have
to find their place again from the start. And if taking focus is enough
to open something, every Tab can throw them somewhere they did not ask
to go.

In Flutter a dialog opened as a route does the first two by itself:
the route takes keyboard focus when it opens, and gives it back to the
button when it closes, and on Android and iOS the framework sends the
screen reader back too. What it does not do is decide where focus goes
when the button that opened the dialog is gone: that is the app's to do.
On iOS the screen reader has to be sent there as well, since VoiceOver
does not follow keyboard focus, and on Android a move made too soon was
seen to be undone by the framework's own.

## WCAG 2.2

- [2.4.3 Focus Order](https://www.w3.org/TR/WCAG22/#focus-order): when the question opens, the next stop is in it; when it closes, the order goes on from the button that opened it, or from the next one when that is gone. `bad-focus-left-behind` fails it by technique [F85](https://www.w3.org/WAI/WCAG22/Techniques/failures/F85) on both counts, with the keyboard, on every platform.
- [3.2.1 On Focus](https://www.w3.org/TR/WCAG22/#on-focus): a Remove button that takes focus asks nothing until it is pressed. `bad-opens-on-focus` fails it as the failure example of [Understanding 3.2.1](https://www.w3.org/WAI/WCAG22/Understanding/on-focus.html) does, a dialog that opens when a field receives focus.

### Shared code

Used by the examples below.

```dart
/// The trails every example starts with: the last part of each Remove
/// button's identifier, and the trail's name.
const _trails = [
  ('ridge', 'Ridge trail'),
  ('lake', 'Lake loop'),
  ('summit', 'Summit path'),
];

/// Asks whether to remove the trail [name]. Completes with true to remove
/// it, and false or null to keep it. Each example asks in its own way.
typedef _Ask = Future<bool?> Function(
  BuildContext context,
  _TrailsState trails,
  String name,
);

/// One Remove button, drawn the way the example draws its buttons.
typedef _RemoveButton = Widget Function(
  String label,
  VoidCallback onPressed,
  FocusNode focusNode,
);

/// A list of saved trails, each with a button that removes it after asking
/// first, and the number left at the end, so that people and tests can see
/// what a key did.
///
/// When a trail is removed its button goes with it, and the button that
/// had focus is gone. Focus is then put on the next trail's button, or on
/// the one before when the last trail went: keyboard focus at once, and
/// on iOS the screen reader's once the question has gone (see
/// [_TrailsState.remove]).
class _Trails extends StatefulWidget {
  const _Trails({required this.slug, required this.ask, required this.button});

  final String slug;
  final _Ask ask;
  final _RemoveButton button;

  @override
  State<_Trails> createState() => _TrailsState();
}

class _TrailsState extends State<_Trails> {
  final List<(String, String)> _left = [..._trails];
  final Map<String, FocusNode> _nodes = {
    for (final (key, _) in _trails) key: FocusNode(),
  };

  /// One key per button, on the button's own semantics node, for the
  /// screen reader's focus request.
  final Map<String, GlobalKey> _keys = {
    for (final (key, _) in _trails) key: GlobalKey(),
  };

  /// The test identifier of the part [part] of this example.
  String id(String part) => 'i03-${widget.slug}-$part';

  /// The route the question is in, noted by [asking] when the question
  /// is built.
  ModalRoute<Object?>? _question;

  /// Counts the questions asked, so that a screen reader move still to
  /// come after one question is dropped once another has been asked.
  int _asked = 0;

  /// Builds the question [child] and notes the route it is in, which
  /// [remove] waits on. Each example builds its question through this.
  Widget asking(BuildContext routeContext, Widget child) {
    _question = ModalRoute.of(routeContext);
    return child;
  }

  @override
  void dispose() {
    for (final node in _nodes.values) {
      node.dispose();
    }
    super.dispose();
  }

  Future<void> remove((String, String) trail) async {
    final asked = ++_asked;
    final yes = await widget.ask(context, this, trail.$2);
    final question = _question;
    _question = null;
    if (yes != true || !mounted) return;
    final index = _left.indexOf(trail);
    setState(() => _left.remove(trail));
    if (_left.isEmpty) return;
    final next = _left[index < _left.length ? index : _left.length - 1].$1;
    // Keyboard focus. TalkBack on Android and the screen reader on the web
    // follow it, so on those nothing more is sent.
    _nodes[next]!.requestFocus();
    // VoiceOver on iOS does not follow keyboard focus, so it is sent. Not
    // at once: while the question is on screen the page under it is
    // hidden from the screen reader, and once the question's route has
    // gone the framework sends VoiceOver back to the button that opened
    // it, which has just been removed (docs/flutter-limitations.md,
    // FL-442). So this waits for the route to go, and then for one more
    // frame, so that it comes after the framework's. In a browser on an
    // iPhone defaultTargetPlatform is iOS too, and there the event would
    // do nothing.
    if (kIsWeb || defaultTargetPlatform != TargetPlatform.iOS) return;
    await question?.completed;
    await WidgetsBinding.instance.endOfFrame;
    if (asked != _asked || !mounted) return;
    _sendScreenReaderTo(next);
  }

  /// Sends the screen reader to [key]'s button, unless that is no longer
  /// where the user is: the trail has gone, or keyboard focus has moved
  /// off its button since.
  void _sendScreenReaderTo(String key) {
    if (!_left.any((t) => t.$1 == key)) return;
    if (!_nodes[key]!.hasPrimaryFocus) return;
    _keys[key]!.currentContext?.findRenderObject()?.sendSemanticsEvent(
      const FocusSemanticEvent(),
    );
  }

  @override
  Widget build(BuildContext context) {
    return Column(
      crossAxisAlignment: CrossAxisAlignment.start,
      spacing: 8,
      children: [
        Text('Saved trails', style: Theme.of(context).textTheme.titleMedium),
        for (final trail in _left)
          KeyedSubtree(
            key: _keys[trail.$1],
            child: TestId(
              id('remove-${trail.$1}'),
              child: widget.button(
                'Remove ${trail.$2}',
                () => remove(trail),
                _nodes[trail.$1]!,
              ),
            ),
          ),
        Semantics(
          key: ValueKey<String>(id('count')),
          identifier: id('count'),
          child: Text('Saved: ${_left.length}'),
        ),
      ],
    );
  }
}

Widget _materialButton(String label, VoidCallback onPressed, FocusNode node) =>
    TextButton(focusNode: node, onPressed: onPressed, child: Text(label));

/// The question every Material example asks, in an `AlertDialog`.
Widget _materialQuestion(
  BuildContext context,
  _TrailsState trails,
  String name,
) => trails.asking(
  context,
  AlertDialog(
    title: Text('Remove $name?'),
    content: const Text('It goes from your saved trails.'),
    actions: [
      TestId(
        trails.id('cancel'),
        child: TextButton(
          onPressed: () => Navigator.pop(context, false),
          child: const Text('Cancel'),
        ),
      ),
      TestId(
        trails.id('confirm'),
        child: TextButton(
          onPressed: () => Navigator.pop(context, true),
          child: const Text('Remove'),
        ),
      ),
    ],
  ),
);
```

```dart
/// keyboard focus when it opens, so the next Tab is inside it, and when it
```

### `good-cupertino`

_Custom solution: not vetted by a real-world example. See "Custom solutions" near the top of this page._

```dart
/// The Cupertino way to confirm a removal is an action sheet. Its actions
/// take keyboard focus; a `CupertinoAlertDialog`'s do not
/// (docs/flutter-limitations.md, FL-440). On the web Enter is
/// `ButtonActivateIntent`, which neither `CupertinoButton` nor
/// `CupertinoActionSheetAction` handles, so it is added around each
/// (FL-002).
class GoodCupertino extends StatelessWidget {
  const GoodCupertino({super.key});

  @override
  Widget build(BuildContext context) {
    return _Trails(
      slug: 'good-cupertino',
      button: (label, onPressed, node) => _enterToo(
        onPressed,
        CupertinoButton(
          focusNode: node,
          onPressed: onPressed,
          child: Text(label),
        ),
      ),
      ask: (context, trails, name) => showCupertinoModalPopup<bool>(
        context: context,
        builder: (context) => trails.asking(
          context,
          CupertinoActionSheet(
            // The sheet's own grey for these is too faint to read
            // (FL-441), so they are given the label colour.
            title: Text('Remove $name?', style: _label(context)),
            message: Text(
              'It goes from your saved trails.',
              style: _label(context),
            ),
            actions: [
              TestId(
                trails.id('confirm'),
                child: _enterToo(
                  () => Navigator.pop(context, true),
                  CupertinoActionSheetAction(
                    isDestructiveAction: true,
                    onPressed: () => Navigator.pop(context, true),
                    child: const Text('Remove'),
                  ),
                ),
              ),
            ],
            cancelButton: TestId(
              trails.id('cancel'),
              child: _enterToo(
                () => Navigator.pop(context, false),
                CupertinoActionSheetAction(
                  onPressed: () => Navigator.pop(context, false),
                  child: const Text('Cancel'),
                ),
              ),
            ),
          ),
        ),
      ),
    );
  }
}

TextStyle _label(BuildContext context) =>
    TextStyle(color: CupertinoColors.label.resolveFrom(context));

/// Makes Enter on the web activate [child], as Space already does.
Widget _enterToo(VoidCallback onPressed, Widget child) => Actions(
  actions: {
    ButtonActivateIntent: CallbackAction<ButtonActivateIntent>(
      onInvoke: (_) {
        onPressed();
        return null;
      },
    ),
  },
  child: child,
);
```

```dart
class BadOpensOnFocus extends StatefulWidget {
  const BadOpensOnFocus({super.key});

  @override
  State<BadOpensOnFocus> createState() => _BadOpensOnFocusState();
}

class _BadOpensOnFocusState extends State<BadOpensOnFocus> {
  /// The trail whose question was asked when its button last took focus,
  /// so that focus coming back to it from the question does not ask again.
  String? _askedFor;

  @override
  Widget build(BuildContext context) {
    return _Trails(
      slug: 'bad-opens-on-focus',
      ask: (context, trails, name) => showDialog<bool>(
        context: context,
        builder: (context) => _materialQuestion(context, trails, name),
      ),
      button: (label, onPressed, node) => TextButton(
        focusNode: node,
        onPressed: onPressed,
        // Defect: the question opens as soon as the button takes focus,
        // so Tab onto a Remove button moves focus into a dialog: a change
        // of context on focus.
        onFocusChange: (focused) {
          if (!focused || _askedFor == label) return;
          _askedFor = label;
          onPressed();
        },
        child: Text(label),
      ),
    );
  }
}
```

## What each platform exposes

Measured on Flutter 3.47.5, in the good examples unless the row says
otherwise. Keyboard focus and a screen reader's focus are separate rows.

| | Web | Android | iOS |
| --- | --- | --- | --- |
| Keyboard focus when a dialog opens | the dialog route's scope, so the next Tab is its first control; DOM focus on the dialog's title (none for the action sheet) | the same | the same |
| Keyboard focus when it closes | back on the button that opened it | the same | the same |
| Keyboard focus when that button is removed | where the app puts it, `requestFocus`; left alone, the control focused before it | the same | the same |
| Screen reader when a dialog opens | VoiceOver follows DOM focus: the title, the action sheet as a whole, Cancel in `good-widgets` | TalkBack to the dialog's title | VoiceOver to the dialog's title |
| Screen reader when it closes | back on the button, with DOM focus | back on the button: the framework asks for it. TalkBack reads the screen's title, then the button | back on the button: the framework asks for it |
| Screen reader when the button is removed | on the next button: it follows `requestFocus` | on the next button: TalkBack follows `requestFocus`, and the examples send nothing more; in the probe, `requestFocus` alone once left it on Back and once on the row above ([FL-442](../flutter-limitations.md#fl-442)) | on the next button, with a `FocusSemanticEvent` sent one frame after the dialog's route has gone. `requestFocus` alone does not move VoiceOver, which goes to the top of the screen |
| `onFocusChange` that opens a dialog | keyboard focus and VoiceOver's cursor both set it off | keyboard focus does; TalkBack's does not | keyboard focus does; VoiceOver's cursor does not |

Things to know:

- **Open dialogs as routes.** `showDialog`, `showCupertinoModalPopup`,
  `showModalBottomSheet`, and `showGeneralDialog` move keyboard focus in
  and back, and the screen reader with it. A panel put on the screen
  with an `OverlayEntry` or a `Stack` gets none of this: it took no focus,
  came last in the Tab order, and dropped focus to the top of the screen
  when it closed ([probe](../evidence/probes/i03/README.md)).
- **Do not turn a route's focus off.** `requestFocus: false` leaves focus
  behind the dialog (`bad-focus-left-behind`).
- **When the control that had focus goes, put focus somewhere on
  purpose.** Flutter gives it to whichever control was focused before,
  which depends on how the user got there. `FocusNode.requestFocus` on
  the next control moves keyboard focus, and TalkBack and VoiceOver on
  the web with it; VoiceOver on iOS needs a `FocusSemanticEvent`.
- **On iOS, send VoiceOver on once the dialog's route has gone.** On
  Android and iOS the framework sends the screen reader back to the
  button that opened the dialog once the dialog's route has gone, even
  when the button has been removed
  ([FL-442](../flutter-limitations.md#fl-442)). VoiceOver on iOS does not
  follow `requestFocus`, so the good examples send a `FocusSemanticEvent`
  to the next button: they note the question's route when its builder
  runs, wait for `ModalRoute.completed`, which completes as the route is
  disposed, and then for one more frame, so that the event comes after
  the framework's. Until the route has gone the page under it is hidden
  from the screen reader, so there is no fixed delay in which the user
  can move on and be pulled back: a move made once VoiceOver has spoken
  the next button stays where it went. VoiceOver took 1.4 to 1.7 s after
  the double tap to speak it, and a move made before that is not covered
  ([FL-442](../flutter-limitations.md#fl-442)). The event is not sent if a new
  question has been asked, the trail has gone, or keyboard focus has left
  the button. On Android, where TalkBack follows `requestFocus`, and on
  the web, where the screen reader follows DOM focus, which follows
  `requestFocus`, nothing is sent. The examples test `kIsWeb` as well as
  `defaultTargetPlatform`: in a browser on an iPhone `defaultTargetPlatform`
  is iOS, and the web engine does nothing with the event (read in the
  source: its handler for `flutter/accessibility` acts only on
  announcements).
- **Open things on activation, not on focus.** `onFocusChange` runs for
  keyboard focus, which on the web includes VoiceOver's cursor.
- **Use an action sheet, not a `CupertinoAlertDialog`, for a Cupertino
  confirmation that a keyboard must answer**
  ([FL-440](../flutter-limitations.md#fl-440)), and add Enter for the web
  ([FL-002](../flutter-limitations.md#fl-002)).

## Flutter limitations

Found on Flutter 3.47.5. Full detail is in the
[limitations log](../flutter-limitations.md).

- [FL-440](../flutter-limitations.md#fl-440): a `CupertinoAlertDialog`'s actions take no keyboard focus. `good-cupertino` uses an action sheet.
- [FL-441](../flutter-limitations.md#fl-441): a `CupertinoActionSheet`'s title and message fail the text contrast check in light mode. `good-cupertino` gives them the label colour.
- [FL-442](../flutter-limitations.md#fl-442): when a route closes, the framework sends the screen reader back to where it was after the app's own move, even when that control has been removed. On iOS the good examples send it on one frame after the route has gone.
- [FL-002](../flutter-limitations.md#fl-002): on the web Enter does not activate a `CupertinoButton` or a `CupertinoActionSheetAction`. `good-cupertino` adds it.

say it has focus in the widget tests and on Android, by
`document.activeElement` on the web, and on iOS, where XCUITest cannot
see focus, by what Space does there. A stop behind the dialog, out of
the accessibility tree, is named by what Enter or Space does there: it
asks about that trail. The screen reader walks never move the screen
reader after an activation, except where the user's own move is the
point: in the VoiceOver walk on iOS, as soon as VoiceOver has spoken the
next button after a removal, its own command moves its cursor one
element back, and it must still be there three seconds later. TalkBack's focus is read from
`isAccessibilityFocused`, VoiceOver's on iOS by one move back and one
forward again (when a question opens, before any control is touched, one
move forward and one back, both inside the question), and VoiceOver's on
the web from its cursor's position on the screen. The probe's findings and raw output are in
[evidence/probes/i03](../evidence/probes/i03/README.md).

Not yet covered: Full Keyboard Access on iOS; VoiceOver in WebKit;
Switch Access and Switch Control; what each screen reader announces
when a route opens (I12); removing the last trail with a screen reader;
a TalkBack move of TalkBack's own right after a removal (the walk cannot
swipe TalkBack on the emulator; on Android the examples send TalkBack
nothing after a removal, so only the framework's own request could move
it);
and a dialog's role, name, and what is kept out of reach behind it,
which are C08, C09, and C10.
