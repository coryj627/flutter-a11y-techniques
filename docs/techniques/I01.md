# I01 Focusable and clickable controls

Anything that can be tapped can also be reached with the keyboard,
activated with Enter and Space, and activated by assistive technology, and
it acts when the pointer is released over it, not when it goes down.

Code: [`lib/techniques/i01_focusable_controls/examples.dart`](../../lib/techniques/i01_focusable_controls/examples.dart).
Spec: [`docs/specs/I01-focusable-controls.md`](../specs/I01-focusable-controls.md).
In the app: `/t/I01`, and each example at `/t/I01/<slug>`.

A button's name, role, and disabled state are [C01 Button](C01.md), and
roles in general are [S13 Roles and traits](S13.md). The order that focus
moves in, moving focus from code, other keys, Escape, and how focus looks
each have an entry of their own (I02, I03, I04, I08, and V14), not built
yet.

## Why it matters

In Flutter, making something tappable and making it usable from a
keyboard are separate jobs. A `GestureDetector` makes a card answer a
finger; it does not put the card in the Tab order, and it does not make
Enter or Space do anything. Someone who uses a keyboard, a switch, or
another device that moves focus from control to control finds nothing
there, or finds a control they can land on and cannot press.

The pointer has its own trap. A control that acts the moment a finger
touches it gives no chance to change your mind: people with tremors, or
anyone who touches the wrong thing, are used to sliding off before
letting go, and here that does nothing.

And a control has to say it is one. A card made tappable with an `InkWell`
works from the keyboard and by tap, but on Android and iOS a screen reader
reads it as text, so its users do not know they can activate it.

## WCAG 2.2

- [2.1.1 Keyboard](https://www.w3.org/TR/WCAG22/#keyboard): what a tap does can be done from a keyboard, which means reaching the control with Tab and activating it with Enter or Space.
- [2.5.2 Pointer Cancellation](https://www.w3.org/TR/WCAG22/#pointer-cancellation): the press of a pointer does not carry out the function; it happens on release over the control, so moving off first abandons it.
- [4.1.2 Name, Role, Value](https://www.w3.org/TR/WCAG22/#name-role-value): assistive technology is told the control is a button, and which control has keyboard focus.

## Bad examples

Each has one defect, and the tests assert that the defect is present.

| Example | Defect | Fails |
| --- | --- | --- |
| `bad-inkwell-no-role` | `Card(child: InkWell(onTap: ...))`, the tappable card in the `Card` documentation. | `bad-no-focus` | `Semantics(button: true)` around `GestureDetector(onTap: ...)`, with no focus node. A screen reader reads and activates it as a button, but Tab goes past it. | 2.1.1 |

```dart
/// Lays out one example and reports how many times its control was
/// activated, so people and tests can confirm that activation worked.
class _Demo extends StatefulWidget {
  const _Demo({required this.slug, required this.builder});

  final String slug;
  final List<Widget> Function(BuildContext context, VoidCallback activate)
  builder;

  @override
  State<_Demo> createState() => _DemoState();
}

class _DemoState extends State<_Demo> {
  int _count = 0;

  @override
  Widget build(BuildContext context) {
    return Column(
      crossAxisAlignment: CrossAxisAlignment.start,
      spacing: 16,
      children: [
        ...widget.builder(context, () => setState(() => _count++)),
        Semantics(
          key: ValueKey<String>('i01-${widget.slug}-count'),
          identifier: 'i01-${widget.slug}-count',
          liveRegion: true,
          child: Text('Activations: $_count'),
        ),
      ],
    );
  }
}

/// The text every example's control shows.
const _trail = 'Ridge trail';

/// A card drawn by hand: a map icon and the trail's name, with a ring
/// around it when [focused]. It has no semantics of its own beyond its
/// text, and does nothing by itself.
class _TrailCard extends StatelessWidget {
  const _TrailCard({this.focused = false});

  final bool focused;

  @override
  Widget build(BuildContext context) {
    final colors = Theme.of(context).colorScheme;
    return Container(
      constraints: const BoxConstraints(minHeight: 56, minWidth: 220),
      padding: const EdgeInsets.symmetric(horizontal: 16, vertical: 12),
      decoration: BoxDecoration(
        color: colors.surfaceContainerHighest,
        borderRadius: BorderRadius.circular(12),
        border: Border.all(
          color: focused ? colors.onSurface : colors.outline,
          width: focused ? 3 : 1,
        ),
      ),
      child: Row(
        mainAxisSize: MainAxisSize.min,
        spacing: 12,
        children: [
          Icon(Icons.map_outlined, color: colors.onSurfaceVariant),
          Flexible(
            child: Text(_trail, style: TextStyle(color: colors.onSurface)),
          ),
        ],
      ),
    );
  }
}

/// What makes a custom control reachable and usable from the keyboard: a
/// focus node in the traversal order, and Enter and Space mapped to
/// [onActivate]. `WidgetsApp` sends Space as `ActivateIntent` everywhere,
/// and Enter as `ActivateIntent` on Android and iOS and as
/// `ButtonActivateIntent` on the web, so both intents are handled. The
/// builder is told whether to show the focus ring. It adds no role, name,
/// or semantics action.
class _Keyboard extends StatefulWidget {
  const _Keyboard({required this.onActivate, required this.builder});

  final VoidCallback onActivate;
  final Widget Function(bool focused) builder;

  @override
  State<_Keyboard> createState() => _KeyboardState();
}

class _KeyboardState extends State<_Keyboard> {
  bool _focused = false;

  Object? _activate(Intent intent) {
    widget.onActivate();
    return null;
  }

  @override
  Widget build(BuildContext context) {
    return FocusableActionDetector(
      mouseCursor: SystemMouseCursors.click,
      actions: {
        ActivateIntent: CallbackAction<ActivateIntent>(onInvoke: _activate),
        ButtonActivateIntent: CallbackAction<ButtonActivateIntent>(
          onInvoke: _activate,
        ),
      },
      onShowFocusHighlight: (value) => setState(() => _focused = value),
      child: widget.builder(_focused),
    );
  }
}
```

```dart
/// A `CupertinoListTile` with `onTap` answers a tap only: it takes no
/// keyboard focus on any platform, and it sets no button flag, so it is not
/// a button on Android and iOS (docs/flutter-limitations.md, FL-400). The
/// keyboard half and the flag are added around it.
class GoodCupertino extends StatelessWidget {
  const GoodCupertino({super.key});

  @override
  Widget build(BuildContext context) {

      slug: 'good-cupertino',
      builder: (context, activate) => [
        TestId(
          'i01-good-cupertino-trail',

                  title: const Text(_trail),
                  trailing: const CupertinoListTileChevron(),

                ),
              ),
            ),
          ),
        ),
      ],
    );
  }
```

## What each platform exposes

Measured on Flutter 3.47.5.

| | Web | Android | iOS |
| --- | --- | --- | --- |
| Good card, and the three widgets-layer bad ones | `role="button"`, named "Ridge trail" | `Button`, clickable | button |
| Screen reader on it | "Ridge trail button" | "Ridge trail", "Button", "Double-tap to activate" | "Ridge trail Button" |
| `InkWell` card | `role="button"` ([FL-006](../flutter-limitations.md#fl-006)) | `View`, clickable | static text |
| Screen reader on it | "Ridge trail button" | "Ridge trail", "Double-tap to activate" | "Ridge trail" |
| Can take focus | `tabindex="0"`; none on `bad-no-focus` | `isFocusable` is true for every node with a name or an action, so it shows nothing | not exposed |
| Has focus | `document.activeElement` | `isFocused`, set from Flutter's focus | not exposed: `hasFocus` is always false |
| Keyboard driven by | Playwright | `input keyevent` | XCUITest `typeKey`, with Enter typed as `"\n"` |

TalkBack's lines are what it said with focus moved to each node by the
test. The web lines are VoiceOver on macOS in Chromium and WebKit.

Things to know:

- **Use a widget that is already a control when there is one.** A
  `ListTile` with `onTap`, or any Material button, has focus, the keys,
  release-to-act, and the role.
- **A `CupertinoListTile` with `onTap` takes no keyboard focus, and is
  not a button on Android and iOS**
  ([FL-400](../flutter-limitations.md#fl-400)). On the web it is a button,
  as anything with a tap action is there, but Tab still skips it. Wrap it
  as `good-cupertino` does, and draw a focus ring, since it shows none.
- **An `InkWell` is not a button on Android and iOS**
  ([FL-401](../flutter-limitations.md#fl-401)); on the web it is one,
  from its tap action. Put `Semantics(button: true)` around it, or use a
  `ListTile`.
- **`Focus` is not enough for a custom control.** It puts the control in
  the Tab order and leaves Enter and Space doing nothing. Use
  `FocusableActionDetector` with actions for both `ActivateIntent` and
  `ButtonActivateIntent`: on the web Enter arrives as the second
  ([FL-002](../flutter-limitations.md#fl-002)), and a control that
  handles only the first ignores Enter there.
- **Act in `onTap`, not `onTapDown`.** `onTap` runs when the pointer is
  released over the control, and not at all if it leaves first.
- **A screen reader does not need keyboard focus.** It activates a control
  through its tap action, so `bad-no-focus` works with TalkBack and
  VoiceOver. That is why the keyboard has to be checked on its own.
- **On iOS with Full Keyboard Access**, the engine's source says the
  system's focus goes to every node with a tap action and activates
  through it, apart from Flutter's own focus. If so, `bad-no-focus` would
  be reachable there. This was not observed: with Full Keyboard Access on
  in the simulator, XCUITest's keys did not reach the app at all
  ([probe](../evidence/probes/i01/README.md)).

## Flutter limitations

Found on Flutter 3.47.5. Full detail is in the
[limitations log](../flutter-limitations.md).

- [FL-400](../flutter-limitations.md#fl-400): a `CupertinoListTile` with `onTap` takes no keyboard focus on any platform, and is not a button on Android and iOS. `good-cupertino` adds both.
- [FL-401](../flutter-limitations.md#fl-401): an `InkWell` with `onTap` is not a button on Android and iOS. `good-material` uses a `ListTile`, which is.
- [FL-002](../flutter-limitations.md#fl-002): on the web Enter is `ButtonActivateIntent`, so a control that handles only `ActivateIntent` ignores Enter there. The good examples handle both.
- [FL-006](../flutter-limitations.md#fl-006): on the web any node with a tap action is a button, so `bad-inkwell-no-role` has its role there.

The keyboard is pressed on every layer: in the widget tests, in Chromium,
on the Android emulator with `input keyevent`, and on the iOS simulator
with XCUITest's hardware keys. On Android the test reads which node has
focus; on iOS it cannot, so it shows focus by what the next key does:
Enter or Space activates the control that has focus, and on Back leaves
the screen. Every check that a key did nothing is followed, in the same
run, by the same key doing something on Back, so a key that never
arrived cannot pass as a key that was ignored. The pointer test presses
each card and slides off before letting go.
